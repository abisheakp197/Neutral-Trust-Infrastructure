NTI Witness Evidence Package

Fixed verification location for external witnesses

This directory is the stable location where external witnesses (such as HORIZON SHIELD) recompute and verify the cryptographic state of Neutral Trust Infrastructure. Every artifact is an input to be re-derived, not a claim to be accepted.

Artifacts

  • MANIFEST.json — SHA-256 of the witness generator, the sample evidence fixture, and NTI's native test scripts, plus key_url and key_history.
  • RESULTS.json — NTI's native suite outcomes plus the S4/S5/S6 seal values.
  • PUBLIC_KEY.pem — Ed25519 public key (trust anchor: key_url).
  • SIGNATURE.sig — 64-byte Ed25519 signature over a domain-separated, length-prefixed encoding of RESULTS.json and MANIFEST.json.
  • verify.sh — self-contained verifier: package signature, S4/S5/S6 seals, all manifest hashes, and the key fingerprint.
  • README.md — full documentation.

How to verify

cd docs/witness && ./verify.sh /path/to/Neutral-Trust-Infrastructure

The verifier checks the package signature, recomputes the S4/S5/S6 seals, re-hashes every file in MANIFEST.json, and confirms the published key fingerprint. See the README for the exact bytes the package signature covers.

The S4 / S5 / S6 seals

NTI's own native implementation, Apache-2.0. It shares no code with any external conformance kit. Generator: conformance/witness_generator/generate_seals.py.

SealFieldConstruction
S4 file integrityS4_file_integritySHA-256 of each evidence artifact
S5 evidence rootS5_evidence_rootRFC 6962 Merkle Tree Hash over the S4 digests (domain-separated; odd node promoted, never duplicated)
S6 sealS6_hmac_sealEd25519 signature over the S5 root plus the leaf count and artifact names

The S6 field is named S6_hmac_seal to match the witness spec, but the construction is a signature, not an HMAC. An HMAC needs a shared secret, which a witness cannot verify without holding it; a signature verifies with the public key alone.

Cryptographic hardening

The packaging logic was hardened against four structural weaknesses:

  • Package signature: domain-separated and length-prefixed. Each file is digested on its own, so a byte cannot be moved between RESULTS.json and MANIFEST.json.
  • Merkle tree: the odd node on a level is promoted unchanged (RFC 6962), not duplicated, so two different leaf sets cannot collapse to the same root.
  • S6: signs the root and the leaf count and artifact names, so a valid root cannot be shown for a different artifact set.
  • Trust anchor: MANIFEST.json carries a key_url pointing at the GitHub Pages copy of the public key, fetched out of band.

Key history

MANIFEST.json carries a key_history block recording each Ed25519 key's fingerprint, status, and validity window. When the signing key changes, the previous key is marked retired and the new key is added, so a rotation is recorded rather than silently replacing the old key.

Scope and limits.

  • The S4/S5/S6 seals are computed over a synthetic fixture (sample_evidence.json). They prove the mechanism works; they are not seals over production evidence. The suite results below are separate and real.
  • No third-party or external conformance suite is included or referenced.
  • Trust anchor. MANIFEST.json carries a key_url pointing at the GitHub Pages copy of the public key, fetched out of band. The private key is not published, so a valid signature proves the files are intact under that key, not who holds it.
